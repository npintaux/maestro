# Master Lifecycle Conductor (Phases 0–6)

## Overview
This skill embodies the **Master Conductor** persona for Maestro. It acts as the state-machine controller that sequences the entire software engineering lifecycle from raw prompt to production-ready Cloud Run service.

The Conductor orchestrates specialized subagents with clean context boundaries, prompts the human user at mandatory checkpoints (Gate 0.5 ADR sign-off), runs mechanical gate scripts, and manages bounded remediation loops when gates fail.

The Conductor possesses **zero authority to waive mechanical gates**; phase progression is strictly conditional on deterministic script exit codes (`$? == 0`).

### Plugin & Workspace Isolation Rules
- **Never copy `scripts/` or `archetypes/` into the target workspace**: Maestro gate scripts and pattern blueprints reside inside the plugin bundle (`$HOME/.gemini/config/plugins/maestro/` or relative to the skill). Blueprints are read in-place as reference templates; the target workspace receives only generated `docs/`, `src/modules/`, `tests/`, and `deploy/` files.
- **Gate script execution**: In a target workspace, execute gates via the plugin path:
  `uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run <gate>` (or `python3 scripts/gate_controller.py` when developing inside the plugin repository itself).
- **Runtime `.maestro/` directory**: The `.maestro/` folder in the target workspace root is automatically generated by the gate controller to track phase states and cryptographic RED-lock test manifests.

## When to Use
Use when:
- Orchestrating a complete software engineering project from scratch (`/conduct "build a URL redirect resolver"`).
- Running an end-to-end pipeline starting from an existing PRD (`/conduct --from-prd docs/PRD.md`).
- Executing an end-to-end vertical slice or "spine run" to validate the full gate chain.
- Managing multi-subsystem coordination, phase transitions, and subagent delegation.

Do **not** use for:
- Writing raw domain Python code or unit tests directly (delegate to `/code-implement`).
- Designing subsystem OpenAPI schemas and SPEC files in isolation (delegate to `/lead-decompose`).
- Performing isolated threat modeling or IAM audits (delegate to `/secops-audit`).
- Generating contract or behavioral test suites (delegate to `/test-architect`).

## Core Process

```
Phase 0 (PRD) ──▶ Phase 1 (Arch & Sec) ──▶ Gate 0.5 (HITL) ──▶ Phase 2 (Decompose) ──▶ Phase 3 (Tests) ──▶ Phase 4 (Code) ──▶ Phase 5 (Release) ──▶ Phase 6 (Done)
```

Consult `references/orchestration-state-machine.md` for the complete transition matrix and `references/subagent-dispatch-templates.md` for subagent prompt templates.

### Phase 0: Product Intake & Requirements Gate
1. Invoke the **Product Owner** persona (`/prd-validate`) via `invoke_subagent` (Template 1, `TypeName: "self"`).
2. Produce `docs/PRD.md` with:
   - Functional Requirements (FR-1, FR-2, ...)
   - Non-Functional Requirements covering all 7 GCP WAF pillars (Security, Reliability, Cost, Ops, Perf, Scale, Sustainability)
   - Zero unresolved placeholders (`<...>`, `TODO`, `TBD`).
3. Verify `docs/PRD.md` exists and is non-empty before advancing.

---

### Phase 1: Macro-Architecture, ADRs & Security Posture
1. Invoke the **Lead Cloud Architect** persona (`/architect-design`) via `invoke_subagent` using Template 2 to produce:
   - `docs/adr/0001-<slug>.md` (MADR records for compute, datastore, messaging, auth)
   - `docs/architecture.md` (GCP service topology and WAF mappings)
2. In parallel, invoke the **Security Architect** persona (`/secops-audit`) via `invoke_subagent` using Template 3 to produce:
   - `docs/security.md` (STRIDE threat matrix, IAM least-privilege matrix, secret inventory)
3. Execute the Phase 1 initial structural gates via the Gate Controller:
   ```bash
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-0
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-1
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-security
   ```
4. **Structured Adversarial Review (Elephant-Goldfish Protocol)**:
   - **MANDATORY**: Dispatch 3 independent critic subagents concurrently using a single `invoke_subagent` tool call with 3 subagent definitions:
     - Subagent 1: `TypeName: "self"`, `Role: "Resilience Critic"`, `Prompt: <Template 3B with critic_lens="resilience">`
     - Subagent 2: `TypeName: "self"`, `Role: "Cost Critic"`, `Prompt: <Template 3B with critic_lens="cost">`
     - Subagent 3: `TypeName: "self"`, `Role: "Simplicity Critic"`, `Prompt: <Template 3B with critic_lens="simplicity">`
   - *Guardrail*: **NEVER** simulate the 3 critics in the main conductor context. Always issue a single concurrent `invoke_subagent` call so each lens reasons in its own isolated context. (Note: real independence is guaranteed by the host dispatch mechanism, not by the mechanical gate below — the gate only verifies that three distinct, well-formed critic objection sets exist and are fully resolved.)
   - The 3 subagents generate `docs/adr/objections/resilience.json`, `docs/adr/objections/cost.json`, and `docs/adr/objections/simplicity.json`.
   - The Architect evaluates all objections, updates `docs/adr/`, and records resolutions in `docs/adr/objections/resolutions.json`.
   - Run the mechanical adversarial review gate:
     ```bash
     uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-adversarial
     ```

---

### Gate 0.5: Human-In-The-Loop Architectural Sign-Off (MANDATORY CHECKPOINT)
1. **Pause execution**. Do not invoke subsystem decomposition until the human user approves the ADRs and adversarial review resolutions.
2. Present a summary of all proposed ADRs and resolved objections to the user with links to `docs/adr/` and `docs/adr/objections/resolutions.json`.
3. Request explicit approval. Once the user approves:
   - Ensure each accepted ADR has `* **Approved-by**: <user_handle>` and `* **Status**: accepted`.
4. Validate the mechanical approval token via the Gate Controller:
   ```bash
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-0.5
   ```
5. Advancement is strictly blocked until this command exits `0`.

---

### Phase 2: Subsystem Micro-Decomposition & Contract Gate
For each subsystem identified in `docs/architecture.md` (e.g. `src/modules/<subsystem>/`):
1. Invoke the **Subsystem Tech Lead** persona (`/lead-decompose`) via `invoke_subagent` using Template 4 (`TypeName: "self"`).
2. Produce:
   - `src/modules/<subsystem>/openapi.yaml` (complete OpenAPI 3.x contract)
   - `src/modules/<subsystem>/SPEC.md` (domain pattern selection and class structure)
3. Execute the mechanical contract gate:
   ```bash
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-2 --subsystem <subsystem>
   ```
4. Advancement to Phase 3 is blocked until this command exits `0`.

---

### Phase 3: Orthogonal Test Generation & RED-Lock Gate
For each subsystem:
1. Invoke the **Independent Test Architect** persona (`/test-architect`) via `invoke_subagent` (Template 5, `TypeName: "self"`) with `MAESTRO_ACTIVE_ROLE=test-author`.
2. Produce:
   - `tests/contract/<subsystem>/test_contract_<subsystem>.py` (status-code & schema verification)
   - `tests/behavioral/<subsystem>/test_behavioral_<subsystem>.py` (PRD user-story assertions)
3. Invariant: Tests must be generated orthogonally from `docs/PRD.md` and `openapi.yaml` without reading or generating implementation code.
4. **Capture Cryptographic RED-Lock**:
   Verify orthogonal tests fail cleanly against unimplemented domain code and capture SHA256 hashes:
   ```bash
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/verify_red_suite.py" lock --subsystem <subsystem>
   ```
5. Advancement to Phase 4 requires an active RED-lock manifest in `.maestro/red_lock/<subsystem>.json`.

---

### Phase 4: Clean-Architecture TDD Implementation & Gate Suite
For each subsystem:
1. Invoke the **Specialist Implementer** persona (`/code-implement`) via `invoke_subagent` (Template 6, `TypeName: "self"`) with `MAESTRO_ACTIVE_ROLE=implementer`.
2. Implement domain code following the TDD Red-Green-Refactor loop and pattern blueprint (restricted by boundary guard from modifying `tests/contract/` or `tests/behavioral/`).
3. Execute mechanical code quality & test gates via the Gate Controller:
   ```bash
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-3 --subsystem <subsystem>
   uv run python3 "${MAESTRO_PLUGIN_DIR:-$HOME/.gemini/config/plugins/maestro}/scripts/gate_controller.py" run gate-4 --subsystem <subsystem>
   ```
4. Gate 4 automatically verifies RED-lock integrity via `verify_red_suite.py check` before running coverage suites.
5. **Mechanical Remediation Loop (Max 3 Attempts Enforced by Controller)**:
   - If exit code is `0` $\to$ Phase 4 complete.
   - If exit code is `1` $\to$ Capture JSON failure diagnostics emitted by `gate_controller.py`.
   - Dispatch targeted repair task (Template 7) to `/code-implement` with failure trace.
   - If exit code is `3` (Circuit Breaker Tripped) $\to$ **HALT execution immediately** and escalate to human user.

---

### Phase 5: Release Engineering & Deployment Scaffolding
1. Scaffold production deployment assets:
   - `deploy/Dockerfile` (multi-stage non-root container)
   - `deploy/cloudbuild.yaml` (Cloud Build CI/CD pipeline)
   - Container smoke-test script
2. Verify local buildability and container health check.

### Phase 6: Final Delivery & Master Audit Record
1. Compile the master audit record summarizing all gate runs, test coverage, and artifact links.
2. Present the finished solution to the user with a comprehensive traceability matrix ($PRD \leftrightarrow ADR \leftrightarrow Contract \leftrightarrow Code \leftrightarrow Tests \leftrightarrow Deploy$).

## Invariants & Guardrails

1. **Zero LLM Discretion on Gate Verdicts**:
   - The exit code of the mechanical script (`$?`) is the sole arbiter of a gate pass.
   - Never rationalize a failure or proceed with a non-zero exit code.
2. **Mandatory Gate 0.5 Human Sign-Off**:
   - Subsystem implementation cannot start without human approval in `docs/adr/`.
3. **Clean Context Boundaries**:
   - Subagents must be dispatched with targeted prompt templates and explicit file paths, never bloated history.
4. **Strict Boundary Guard**:
   - Worker agents must only modify files within their assigned subsystem boundary (`src/modules/<subsystem>/`).

## Common Rationalizations

| The Rationalization | The Reality |
|---|---|
| *"The test failed due to a minor lint issue, I'll proceed to Phase 5."* | Never proceed on non-zero exit code. Fix it in the remediation loop. |
| *"I can approve the ADRs myself to speed up the run."* | Gate 0.5 is an explicit Human-in-the-Loop checkpoint. Only the human can approve. |
| *"I'll implement the code and write tests in the same subagent."* | Test Architect and Implementer must remain orthogonal personas to prevent self-fulfilling test bias. |
| *"I'll retry until it works."* | Retries are strictly capped at 3 attempts to prevent runaway loops and token drain. |
